# Security

ระบบถือเอกสารการเงินของบริษัทลูกค้า ความเสียหายที่แรงที่สุดมี 3 แบบ: ข้อมูลรั่วข้าม tenant, เอกสารปลอมหลอกให้จ่ายเงิน และข้อมูลส่วนบุคคลรั่ว ทุกหัวข้อด้านล่างกันอย่างใดอย่างหนึ่งใน 3 แบบนี้

## 1. การยืนยันตัวตน

### Member

| วิธี | กติกา |
| --- | --- |
| Magic link ทางอีเมล | token สุ่ม 32 ไบต์ ใช้ได้ครั้งเดียว อายุ 15 นาที เก็บเฉพาะ hash |
| LINE Login | ตรวจ ID token ฝั่ง server (ลายเซ็น, `aud` = channel ID ของเรา, `exp`, `nonce`) |
| MFA | TOTP บังคับสำหรับ `firm_owner` และ `platform_admin` ก่อนเปิดเฟส 1 ให้ลูกค้าจ่ายเงิน |

### Session

- cookie `HttpOnly`, `Secure`, `SameSite=Lax`
- หมดอายุเมื่อไม่ใช้งาน 12 ชั่วโมง หรือครบ 7 วันนับจากเข้าระบบ
- เปลี่ยน session ID ทุกครั้งที่เข้าระบบหรือเปลี่ยน Role
- request ที่เปลี่ยนข้อมูลต้องมี `X-CSRF-Token` ที่ตรงกับ session

### Submitter

- ไม่มีรหัสผ่าน ระบุตัวด้วย LINE user ID ในกลุ่มที่เชื่อมแล้ว หรืออีเมลผู้ส่งที่อยู่ในรายชื่อ
- หน้า LIFF ตรวจ LIFF ID token ฝั่ง server ทุกครั้ง
- Submitter ส่งเอกสารได้อย่างเดียว ดูเอกสารของคนอื่นไม่ได้

## 2. สิทธิ์

| สิทธิ์ | `firm_owner` | `firm_staff` | Submitter | `platform_admin` |
| --- | --- | --- | --- | --- |
| ส่งเอกสาร | ได้ | ได้ | ได้ (เฉพาะบริษัทตัวเอง) | ไม่ได้ |
| ดูเอกสาร, Field, Finding | ได้ | ได้ | ไม่ได้ | เฉพาะผ่าน break-glass |
| แก้ Field, ปิด Finding, Review Task | ได้ | ได้ | ไม่ได้ | ไม่ได้ |
| ส่งออก | ได้ | ได้ | ไม่ได้ | ไม่ได้ |
| ยกเลิก Export, ลบเอกสาร | ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |
| จัดการ Member และ Client Company | ได้ | เพิ่ม Client Company ได้ | ไม่ได้ | ไม่ได้ |
| ดู usage และจ่ายเงิน | ได้ | ไม่ได้ | ไม่ได้ | ดู usage ได้ |
| เริ่ม Leakage Scan | ไม่ได้ (เฟส 1) | ไม่ได้ | ไม่ได้ | ได้ |

ตรวจสิทธิ์ที่ชั้น service ด้วยฟังก์ชันกลางใน `identity` ไม่ตรวจเฉพาะที่ router

### Break-glass

`platform_admin` ดูข้อมูลลูกค้าได้เมื่อเปิดคำขอพร้อมเหตุผลและเลข ticket เท่านั้น สิทธิ์อยู่ได้ 2 ชั่วโมง ทุกการเข้าถึงลง `audit_events` และแจ้ง `firm_owner` ของ Firm นั้นทางอีเมล

## 3. การแยก tenant

- ทุกตารางข้อมูลลูกค้ามี `firm_id` และเปิด row-level security: `USING (firm_id = current_setting('app.firm_id')::uuid)`
- แอปตั้ง `SET LOCAL app.firm_id` ต้น transaction จาก session เท่านั้น ห้ามรับค่านี้จาก request body หรือ query string
- database role ของแอปไม่มีสิทธิ์ `BYPASSRLS` งานข้าม tenant (เช่นรายงานรวมของทีมเรา) ใช้ role แยกที่อ่านได้เฉพาะตาราง usage และ metric
- object key ของไฟล์ขึ้นต้นด้วย `firm_id` และ signed URL ออกให้หลังตรวจสิทธิ์แล้วเท่านั้น
- ทุก endpoint ต้องมี test ว่า Member ของ Firm อื่นได้ 404

## 4. Rate limit

ใช้ token bucket ใน Redis ค่าด้านล่างเป็นค่าเริ่มต้น ปรับได้ใน config

| ขอบเขต | จำกัด |
| --- | --- |
| ขอ magic link ต่ออีเมล | 5 ครั้งต่อ 15 นาที |
| ขอ magic link ต่อ IP | 20 ครั้งต่อชั่วโมง |
| API ต่อ session | 120 คำขอต่อนาที |
| อัปโหลดต่อ Client Company | 60 ไฟล์ต่อนาที |
| เอกสารจาก LINE ต่อ Submitter | 200 ฉบับต่อชั่วโมง เกินแล้วตอบใน LINE ว่ารับต่อพรุ่งนี้ |
| Document Request ต่อ Client Company | 3 ครั้งต่อวัน |
| Leakage Scan ต่อ Firm | 2 งานพร้อมกัน |
| งบ AI ต่อ Firm | 3 เท่าของค่าเฉลี่ยรายวันของ Firm นั้น หรือ 500 บาทต่อวันสำหรับ Firm ใหม่ ถึงแล้วเอกสารรอคิวถึงวันถัดไปและแจ้งทีมเรา |
| เรียก RD VAT Service ทั้งระบบ | 2 คำขอต่อวินาที |

webhook ของ LINE ไม่จำกัดที่ขาเข้า เพราะต้องตอบ 200 เสมอ จำกัดที่ขั้นประมวลผลต่อ Submitter แทน

## 5. Webhook

- LINE: ตรวจ `x-line-signature` ตาม `docs/API_SPEC.md` ก่อนอ่าน body
- Email: ตรวจ signature ของผู้ให้บริการ และจำกัดขนาด email รวม 25 MB
- ตัดเหตุการณ์ซ้ำด้วย event ID ทุกครั้ง
- secret ของ webhook หมุนได้โดยรองรับ secret เก่าและใหม่พร้อมกัน 24 ชั่วโมง

## 6. ไฟล์อัปโหลด

| กติกา | ค่า |
| --- | --- |
| ชนิดที่รับ | JPEG, PNG, HEIC, WebP, PDF, XML (e-Tax), ZIP (เฉพาะ Leakage Scan) |
| ขนาดต่อไฟล์ | ไม่เกิน 20 MB |
| ขนาดต่องาน Leakage Scan | ไม่เกิน 2 GB และไม่เกิน 5,000 ไฟล์ |
| ตรวจชนิดไฟล์ | จาก magic bytes ไม่เชื่อนามสกุลหรือ Content-Type |
| สแกนมัลแวร์ | ก่อนประมวลผลทุกไฟล์ |
| PDF | แปลงเป็นภาพฝั่ง server ไม่รัน JavaScript หรือฟอร์มใน PDF |
| ZIP | ตรวจอัตราขยายไฟล์และจำนวนไฟล์ก่อนแตก กัน zip bomb และ path traversal |

| ที่เก็บ | key สุ่ม ไม่ใช้ชื่อไฟล์เดิม ไฟล์ต้นฉบับเขียนครั้งเดียว |
| การเข้าถึง | ผ่าน signed URL อายุ 5 นาทีเท่านั้น |

## 7. เนื้อหาเอกสารและ LLM

- ข้อความในเอกสารเป็นข้อมูลที่ไม่น่าเชื่อถือเสมอ ใส่ในแท็ก `<document>` ของ prompt และบอกโมเดลว่าเป็นข้อมูล
- การเรียก LLM เพื่อดึงข้อมูลไม่มี tool และไม่มีสิทธิ์ทำอะไรนอกจากตอบ JSON
- ระบบไม่เปิด URL, QR code หรือเบอร์โทรที่อยู่ในเอกสารโดยอัตโนมัติ
- ข้อความในเอกสารที่ขอให้เปลี่ยนเลขบัญชี ขอให้โอนด่วน หรือสั่งให้ข้ามการตรวจ ถูกบันทึกเป็นหลักฐานของ Finding และไม่มีผลต่อการทำงาน
- ผู้ให้บริการ LLM และ OCR ต้องมีสัญญาว่าไม่นำข้อมูลของเราไปฝึกโมเดล และลบข้อมูลตามระยะที่ตกลง

## 8. ข้อมูลส่วนบุคคลและ PDPA

### ชั้นข้อมูล

| ชั้น | ตัวอย่าง | การปฏิบัติ |
| --- | --- | --- |
| สาธารณะ | ข้อมูลผู้จด VAT จากกรมสรรพากร | เก็บรวมได้ ไม่ผูก tenant |
| ความลับทางธุรกิจ | เอกสารการเงิน, ยอดเงิน, ชื่อคู่ค้า | เข้ารหัส, แยก tenant |
| ข้อมูลส่วนบุคคล | ชื่อ, เบอร์โทร, อีเมล, เลขประจำตัวประชาชนของบุคคลธรรมดา, ภาพลายเซ็น, LINE user ID | เข้ารหัส, ปิดบังใน log, ลบตามนโยบาย |
| ข้อมูลบัญชีธนาคาร | เลขบัญชีผู้ขาย | เก็บ hash กับเลข 4 ตัวท้าย ค่าเต็มอยู่ในไฟล์ต้นฉบับเท่านั้น |

### กติกา

- เข้ารหัสขณะเก็บ (ฐานข้อมูล, object storage, backup) และขณะส่ง (TLS 1.2 ขึ้นไป)
- ทำสัญญาประมวลผลข้อมูล (DPA) กับทุก Firm โดยเราเป็นผู้ประมวลผลข้อมูล
- เปิดเผยรายชื่อผู้ประมวลผลช่วง (cloud, LINE, OCR, LLM) และประเทศที่ข้อมูลไปถึง
- log ปิดบังเลขประจำตัวประชาชน เบอร์โทร อีเมล และเลขบัญชี เหลือเฉพาะ 4 ตัวท้าย
- ยกเลิกสัญญาแล้วลบข้อมูลภายใน 30 วัน ยกเว้นที่กฎหมายบังคับให้เก็บ backup หมดอายุใน 35 วัน
- คำขอใช้สิทธิ์ของเจ้าของข้อมูลส่งต่อให้ Firm ในฐานะผู้ควบคุมข้อมูล และทีมเราช่วยดำเนินการภายใน 7 วัน
- ข้อมูลลูกค้าจริงเข้า Golden Set หรือใช้ปรับโมเดลได้เฉพาะเมื่อ Firm ยินยอมเป็นลายลักษณ์อักษร และปิดบังข้อมูลส่วนบุคคลแล้ว

## 9. ความปลอดภัยการจ่ายเงิน (เฟส 2 ขึ้นไป)

หลักเดียวกับหัวข้อ "การจ่ายเงินอัตโนมัติ" ในแผนธุรกิจ

1. **ไม่ถือเงิน** ระบบสั่งจ่ายจากบัญชีของ Client Company ผ่านธนาคารเท่านั้น (ADR-0002)
2. **policy engine เป็นผู้ตัดสิน** รายการจ่ายอัตโนมัติได้ต่อเมื่อผ่าน Payment Rule ทุกข้อ และเก็บ snapshot ของกฎที่ใช้ไว้กับรายการ
3. **แยกหน้าที่** คนตั้ง Payment Rule ต้องไม่ใช่คนเดียวกับคนเพิ่ม Vendor หรือยืนยัน Vendor Bank Account
4. **บัญชีผู้ขายใหม่หรือเปลี่ยนใหม่** ต้องยืนยันทางช่องทางอื่น (โทรตามเบอร์ที่เคยบันทึก) และรอ 24 ชั่วโมงก่อนใช้จ่ายอัตโนมัติ
5. **วงเงิน** ต่อรายการและต่อวันตาม Payment Rule เกินแล้วส่งให้ Approver
6. **Kill Switch** ปิดการจ่ายอัตโนมัติของ Client Company ได้ทันทีจาก LINE และจากเว็บ
7. **Shadow mode 30 วัน** ก่อนเปิดจ่ายจริงให้ลูกค้าแต่ละราย ระบบบอกว่าจะจ่ายแต่คนยังเป็นคนจ่าย แล้วเทียบผล
8. **credential ของธนาคาร** เก็บต่อ Client Company ใน secret manager ให้สิทธิ์น้อยที่สุดที่ธนาคารอนุญาต
9. **แจ้งเตือนทุกการจ่าย** ทันทีทาง LINE และสรุปรายวันให้ Approver

## 10. Audit log

บันทึกลง `audit_events` ทุกครั้งที่: เข้าระบบ, เปลี่ยน Role, สร้างหรือลบ Client Company, เชื่อมหรือยกเลิกกลุ่ม LINE, แก้ Field, ปิด Finding, ส่งออก, ยกเลิก Export, ลบเอกสาร, break-glass, (เฟส 2) ตั้ง Payment Rule, ยืนยันบัญชีผู้ขาย, อนุมัติ, จ่าย, ใช้ Kill Switch

ตารางนี้เพิ่มอย่างเดียว แอปไม่มีสิทธิ์ UPDATE หรือ DELETE และเก็บตามระยะเดียวกับเอกสารบัญชี

## 11. Secret และ infrastructure

- secret ทุกตัวอยู่ใน secret manager ของ cloud และเข้าแอปผ่าน environment variable ตอน deploy
- ไฟล์ `.env` ใช้เฉพาะ `local` และอยู่ใน `.gitignore` มี `.env.example` ที่ไม่มีค่าจริง
- สแกน secret ก่อน commit (pre-commit hook) และใน CI
- สิทธิ์ cloud ให้น้อยที่สุดต่อ service แยกบัญชี `staging` กับ `production`

## 12. การพัฒนาอย่างปลอดภัย

- ตรวจ dependency ที่มีช่องโหว่ใน CI (`pip-audit`, `pnpm audit`) ช่องโหว่ระดับ high ขึ้นไปห้าม merge
- SAST ใน CI (Semgrep หรือ Bandit)
- PR ที่แตะ `identity`, การแยก tenant, ไฟล์อัปโหลด, webhook หรือการจ่ายเงิน ต้องมีคนทบทวนอย่างน้อย 1 คนนอกจาก agent

## 13. Backup และเหตุฉุกเฉิน

- ฐานข้อมูล: snapshot รายวัน และกู้คืนย้อนเวลาได้ 7 วัน ทดสอบกู้คืนเดือนละครั้ง
- object storage: เปิด versioning
- เหตุข้อมูลส่วนบุคคลรั่ว: ข้อมูลของ Firm (เราเป็นผู้ประมวลผล) แจ้ง Firm ที่ได้รับผลกระทบทันทีภายในเวลาที่ DPA กำหนด เพื่อให้ Firm ในฐานะผู้ควบคุมข้อมูลแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล (สคส.) ได้ภายใน 72 ชั่วโมงนับจากทราบเหตุตามที่ PDPA กำหนด ส่วนข้อมูลที่เราเป็นผู้ควบคุมเอง (เช่นข้อมูลบัญชีของ Member) เราแจ้ง สคส. เอง ให้ทนายยืนยันขั้นตอนก่อนเปิดเฟส 1
