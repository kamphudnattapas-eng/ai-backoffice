# Evals

วิธีวัดความแม่นของการอ่านเอกสารและการตรวจก่อน merge ความแม่นคือสินค้าของเรา การเปลี่ยน prompt โมเดล หรือขั้นตอนใน pipeline โดยไม่รัน eval จึงนับว่างานยังไม่เสร็จ

## Golden Set

ชุด Document ที่มีคำตอบถูกต้องทุก Field และมีคำตอบว่า Check ข้อไหนต้องไม่ผ่าน

### ส่วนประกอบเป้าหมาย

| Document Type | golden-v0 (เฟส 0) | golden-v1 (ก่อนเปิดเฟส 1) |
| --- | --- | --- |
| `tax_invoice_full` | 150 | 500 |
| `tax_invoice_abbreviated` | 50 | 150 |
| `receipt` | 50 | 150 |
| `invoice` | 50 | 150 |
| ประเภทอื่น (ใช้วัดการแยกประเภท) | 50 | 200 |

แต่ละชุดต้องมีทั้งรูปถ่ายมือถือ (เอียง, เงา, เบลอเล็กน้อย), ไฟล์สแกน, PDF จากระบบ และลายมือบางส่วน ในสัดส่วนใกล้เคียงกับที่ลูกค้าส่งจริง

### แหล่งข้อมูล

1. **สังเคราะห์**: สร้างเอกสารปลอมจากแม่แบบ แล้วฝังปัญหาที่รู้คำตอบ เช่นขาดที่อยู่ผู้ซื้อ, ใบซ้ำ, ลายเซ็นก๊อป
2. **ตัวอย่างสาธารณะ**: แบบฟอร์มและตัวอย่างจากหน่วยงานราชการหรือเว็บไซต์ที่อนุญาตให้ใช้
3. **เอกสารจริงที่ลูกค้ายินยอม**: ต้องมีหนังสือยินยอม ปิดบังข้อมูลส่วนบุคคลก่อนเข้าชุด และเก็บใน bucket ส่วนตัว ห้ามอยู่ใน git

### โครงสร้างไฟล์

```text
evals/
├── golden/
│   └── manifest-v1.jsonl      หนึ่งบรรทัดต่อเอกสาร: id, document_type, file_uri, source, labels_path
├── labels/<id>.json            คำตอบของทุก Field + รายการ rule_id ที่ต้อง fail
├── runner/                     ตัวรัน eval
└── results/<YYYY-MM-DD>-<git-sha>.json
```

เอกสารสังเคราะห์อยู่ใน git ได้ เอกสารจริงอ้างถึงด้วย `file_uri` ที่ชี้ไป bucket ส่วนตัวเท่านั้น

### กติกาการติดคำตอบ

- ค่าเงินติดเป็นตัวเลขตามที่พิมพ์ ไม่ปัดเอง
- วันที่ติดทั้งค่าดิบในเอกสาร (เช่น 15/10/69) และค่าที่แปลงแล้วแบบ ค.ศ.
- ช่องที่ไม่มีในเอกสารติด `null` ช่องที่มีแต่อ่านไม่ออกแม้ด้วยตาคนติด `"unreadable"`
- คนติดคำตอบ 2 คนต่อเอกสารใน golden-v1 ถ้าไม่ตรงกัน ให้ที่ปรึกษาบัญชีตัดสิน

## ตัวชี้วัด

| ตัวชี้วัด | นิยาม |
| --- | --- |
| Field accuracy | สัดส่วน Field ที่ค่าหลัง normalize ตรงกับคำตอบ คิดเฉพาะช่องที่บังคับตาม `docs/DATA_MODEL.md` |
| Straight-through rate | สัดส่วน Document ที่ทุกช่องบังคับถูก และไม่ถูกส่งให้คนตรวจ |
| Accuracy after review | Field accuracy เมื่อจำลองว่าคนตรวจแก้ทุกช่องที่ระบบส่งให้ตรวจแล้ว |
| Classification accuracy | สัดส่วน Document ที่แยกประเภทถูก |
| Rule precision | ของ Finding ที่ระบบออก สัดส่วนที่ตรงกับคำตอบ แยกตาม rule_id |
| Rule recall | ของ Finding ที่ควรเกิด สัดส่วนที่ระบบจับได้ แยกตาม rule_id |
| Calibration | ในช่องที่ Confidence ผ่านเกณฑ์ สัดส่วนที่ถูกต้อง |
| Latency | เวลาจาก received ถึง ready ค่ากลางและ p95 |
| Cost per document | ผลรวม `ai_calls.cost_thb` ต่อ Document |

## เกณฑ์

| ตัวชี้วัด | เกณฑ์เปิดเฟส 1 | เป้าเดือนที่ 12 |
| --- | --- | --- |
| Straight-through rate | 70% | 85% |
| Accuracy after review | 95% | 99% |
| Classification accuracy | 95% | 98% |
| Rule precision ของกฎระดับ `critical` | 90% | 95% |
| Rule recall ของกฎระดับ `critical` | 85% | 95% |
| Calibration | 99% | 99.5% |
| Latency (ค่ากลาง) | ไม่เกิน 10 นาที | ไม่เกิน 3 นาที |
| Cost per document | ไม่เกิน 0.50 บาท | ไม่เกิน 0.30 บาท |

เกณฑ์ Confidence ของแต่ละช่องตั้งจาก Calibration: เลือกค่าต่ำสุดที่ทำให้ช่องที่ผ่านเกณฑ์ถูกต้องอย่างน้อยตามเกณฑ์ Calibration

## เมื่อไรต้องรัน

| สถานการณ์ | คำสั่ง | ชุดข้อมูล |
| --- | --- | --- |
| ทุก commit ผ่าน `make check` | `make eval-fast` | 100 เอกสารสังเคราะห์ ใช้ fake OCR/LLM ที่บันทึกผลไว้ |
| แก้ prompt, เปลี่ยนโมเดล, แก้ pipeline, แก้ Check | `make eval` | Golden Set เต็ม เรียกโมเดลจริง |
| ทุกคืนบน branch หลัก | `make eval` | Golden Set เต็ม |

## เกณฑ์ผ่านก่อน merge

- ทุกตัวชี้วัดผ่านเกณฑ์ของเฟสปัจจุบัน
- ไม่มีตัวชี้วัดใดลดลงเกิน 1 จุดเปอร์เซ็นต์จาก baseline ล่าสุดของ branch หลัก
- rule precision ของกฎระดับ `critical` ข้อใดต่ำกว่าเกณฑ์ ถือว่าไม่ผ่าน แม้ค่าเฉลี่ยจะผ่าน

## การรายงาน

- runner บันทึกผลเป็น JSON ใน `evals/results/`
- คำอธิบาย PR แนบตารางเทียบกับ baseline: ตัวชี้วัดทุกตัว ค่าเดิม ค่าใหม่ และส่วนต่าง
- เอกสาร 10 ฉบับที่ผิดมากที่สุดถูกแสดงในรายงานพร้อมเหตุผล เพื่อใช้ปรับรอบถัดไป

## ข้อมูลจาก Correction

Correction ของลูกค้าจริงเป็นแหล่งปรับปรุงที่ดีที่สุด แต่นำเข้า Golden Set หรือใช้ปรับโมเดลได้เฉพาะ Firm ที่ยินยอมเป็นลายลักษณ์อักษร และต้องปิดบังข้อมูลส่วนบุคคลก่อนตาม `docs/SECURITY.md`
